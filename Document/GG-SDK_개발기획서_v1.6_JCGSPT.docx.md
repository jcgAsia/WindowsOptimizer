# **1\. 개요 및 목적**

GG-SDK는 안드로이드 앱의 WebView와 시스템 브라우저(Chrome) 간의 쿠키 저장소 격리 문제를 해결하기 위해 설계된 경량 광고 타겟팅 SDK이다.

앱 실행 시 백그라운드에서 Chrome Custom Tabs(CCT)의 mayLaunchUrl API를 호출하여 서버가 발급하는 Set-Cookie를 시스템 브라우저의 공유 쿠키 저장소(Shared Cookie Jar)에 기록함으로써, 사용자가 이후 브라우저에서 웹서핑 시 광고 타겟팅 정밀도를 향상시킨다.

⚠ 본 SDK는 쿠키를 강제 조작하지 않으며, 안드로이드 표준 API(CustomTabsService)만 사용한다. 단, 안드로이드 15의 CHIPS(쿠키 파티셔닝) 정책이 핵심 변수이므로 개발 착수 전 PoC 검증이 필수다.

# **2\. 모듈 아키텍처 설계**

## **2.1. 설계 원칙**

GG-SDK는 기능과 실행 시점이 서로 다른 로직을 하나의 흐름에 뒤섞지 않도록 5개의 독립 모듈로 분리한다. 각 모듈은 명확한 단일 책임을 가지며, 다른 모듈의 실패가 자신의 실행에 영향을 주지 않도록 설계한다. 모듈 간 통신은 콜백 또는 결과값 전달 방식으로 단방향으로만 흐른다.

⚠ 모듈화의 핵심 이유: 각 모듈을 독립적으로 개발·테스트·교체할 수 있어야 한다. 한 모듈의 버그가 전체 SDK를 멈추게 해서는 안 된다.

## **2.2. 5모듈 구성**

| 모듈 | 이름 | 실행 시점 | 단일 책임 |
| :---: | :---- | :---- | :---- |
| **Module A** | **Config Loader** | 앱 실행 즉시 (독립) | 서버에서 설정 파일을 받아 복호화하여 메모리에 적재. 항상 최우선 실행. |
| **Module B** | **Gate Checker** | A 완료 직후 (동기) | 설정값 기반 조건들을 즉시 판단. 통과/중단 결과를 동기적으로 반환. |
| **Module C** | **Engine Launcher** | B 통과 후 (비동기 대기) | 환경 감지 콜백 대기 \+ startDelay 타이머. D의 실행 진입점 역할. |
| **Module D** | **Launch Engine** | C 준비 완료 후 | CCT 바인딩, mayLaunchUrl 순차 호출, StateTracker 관리. |
| **Module E** | **Log Reporter** | A 완료 직후 (독립) | DAU·접속 로그 비동기 전송. B/C/D 결과와 완전히 무관하게 독립 실행. |

## **2.3. 모듈 실행 흐름**

아래 흐름에서 A와 E는 독립 트랙으로 실행된다. B→C→D는 순차적 체인이며 어느 단계에서든 중단되면 이후 모듈은 실행되지 않는다.

| 단계 | 모듈 | 트랙 | 처리 내용 및 중단 조건 |
| :---: | :---- | :---: | :---- |
| **①** | **Module A** | **독립** | 앱 실행 즉시 설정 파일 로드. 실패 시 재시도. 성공 시 B와 E를 동시에 트리거. |
| **②** | **Module E** | **독립** | A 완료 신호 수신 즉시 로그 전송. B/C/D 결과와 완전히 분리. 실패해도 재시도 없이 종료. |
| **③** | **Module B** | **메인 체인** | forceDown → allowAppVersion → launchUrl → activationRate 순으로 즉시 체크. 하나라도 미통과 시 C·D 실행 안 함. |
| **④** | **Module C** | **메인 체인** | B 통과 후 EnvDetector 결과 대기(비동기). DEV 환경이면 중단. PROD 확정 시 startDelay 타이머 시작. 대기 중 백그라운드 전환 시 중단. |
| **⑤** | **Module D** | **메인 체인** | C 준비 완료 신호 수신 후 CCT 바인딩 → mayLaunchUrl 순차 호출 → StateTracker 기록. |

## **2.4. Module B와 C를 분리한 이유**

Gate Checker(B)와 Engine Launcher(C)를 하나의 모듈로 합치지 않은 이유는 실행 방식이 근본적으로 다르기 때문이다.

| 구분 | Module B — Gate Checker | Module C — Engine Launcher |
| :---- | :---- | :---- |
| **실행 방식** | 동기(Synchronous). 설정값만 보면 즉시 결과 반환. | 비동기(Asynchronous). WebView 콜백과 타이머를 기다린다. |
| **판단 근거** | 설정 파일 값. 앱 실행 시점에 이미 모든 정보 보유. | 환경 감지 결과. WebView가 로드된 후에야 알 수 있다. |
| **결과 시점** | 즉시 (밀리초 단위) | 수 초 후 (WebView 로드 \+ startDelay) |
| **실패 처리** | 단순 중단. 콜백 불필요. | 타이머 취소, 바인딩 해제 등 정리 작업 필요. |

## **2.5. Log Reporter(E)를 독립 모듈로 분리한 이유**

로깅을 B 또는 C 내부에 넣지 않고 독립 모듈로 분리한 근거는 다음과 같다.

| 시나리오 | E를 독립시키지 않으면 발생하는 문제 |
| :---- | :---- |
| **B에서 forceDown으로 중단된 사용자** | 로그가 전송되지 않아 DAU 집계에서 누락. 실제 앱 실행 사용자 수보다 적게 집계됨. |
| **activationRate 미통과 사용자 (예: 90%)** | B에 로그가 있으면 10%만 로그 전송 → DAU가 실제의 10%로 측정됨. 치명적 통계 오류. |
| **C에서 DEV 환경 감지로 중단된 사용자** | 개발자 테스트 접속이 DAU에서 제외되어야 하므로 이 경우는 로그 미전송이 오히려 맞음. E에서 env 파라미터로 필터링하는 방식이 올바름. |
| **향후 D의 URL 호출 성공 로그 추가 시** | E가 독립 모듈이면 D의 결과를 E에 전달하는 인터페이스만 추가하면 됨. 결합도가 낮아 확장이 쉬움. |

✔ E는 A 완료 직후 독립 트리거된다. B가 forceDown으로 전체를 중단해도 E는 이미 실행 완료된 상태다. 이것이 정확한 DAU 집계를 보장하는 핵심 구조다.

# **Module A — Config Loader (설정 파일 독립 로더)**

## **A.1. 핵심 원칙**

Config Loader는 SDK 내 모든 모듈과 독립적으로 작동해야 한다. forceDown 상태이거나 앱이 강제 종료되어도 다음 앱 실행 시 반드시 설정 파일 로딩을 재시도한다. 이 원칙이 깨지면 SDK 원격 제어 자체가 불가능해진다.

⚠ Module A의 독립성은 절대 타협할 수 없다. 다른 모듈 실패가 A의 실행을 막아서는 안 된다.

## **A.2. 설정 파일 구조 (XML 스키마)**

설정 파일은 서버에서 암호화(Base64 \+ AES 등)된 형태로 전송되며, SDK 내부에서 디코딩하여 XML 구조로 파싱한다. 아래는 XML 필드 정의이다.

| 필드명 | 타입/값 | 설명 및 동작 |
| :---- | :---- | :---- |
| **forceDown** | boolean | true: SDK 전체 기능 강제 중단. ConfigManager 제외. 원격 긴급 차단 스위치. |
| **allowAppVersion** | string | 허용 앱 버전 번호. 현재 실행 앱 버전이 이 값과 같거나 낮아야 작동. 상위 버전은 자동 차단(심사 중 방어 로직). |
| **activationRate** | integer (0\~100) | LaunchUrlEngine 실행 확률(%). 앱 실행마다 독립 연산. 0이면 항상 미실행, 100이면 항상 실행. 예: 10 → 10% 확률로만 LaunchUrlEngine 작동. |
| **startDelay** | integer (초) | 모든 실행 조건 통과 후 LaunchUrlEngine 실제 시작까지 대기하는 시간(초). 앱 초기 로딩 자원 경합 방지 목적. 0이면 즉시 시작. |
| **devDetector** | on / off | on: WebView URL 기반 환경 감지 활성화. DEV 환경 감지 시 launchUrl 비활성화. |
| **launchUrl** | on / off | on: mayLaunchUrl 기반 URL 호출 기능 전체 활성화. |
| **url.list** | array\<string\> | 순차 호출할 URL 목록. 중요도 높은 순서로 정렬 필수. 순서가 성능에 직결됨. |
| **ragTime** | integer (초) | URL 리스트 전체 호출 완료 후, 다음 사이클 시작까지 대기 시간(초). |
| **cycleTime** | integer (초) | 리스트 내 URL 개별 호출 간격(초). 호출 후 다음 URL까지 대기. |

## **A.3. 설정 파일 암호화**

* 네트워크 패킷 분석을 통한 구조 노출을 방지하기 위해 설정 파일은 암호화하여 전송한다.

* 암호화 방식은 개발팀 선택 사항이나, 대칭키 방식(AES-128/256) \+ Base64 인코딩 조합을 권장한다.

* 복호화 키는 앱 내 하드코딩하지 않고 별도의 보안 저장소(Android Keystore) 활용을 검토한다.

✔ 암호화 방식 결정 전, 서버-클라이언트 간 키 관리 전략을 먼저 확정해야 한다.

# **Module B — Gate Checker (실행 조건 판단)**

## **B.1. 역할 및 처리 방식**

Gate Checker는 Config Loader(A)가 설정 파일을 메모리에 적재한 직후 실행된다. 설정값만으로 즉시 판단할 수 있는 조건들을 동기적으로 순서대로 체크하며, 하나라도 미통과 시 이후 모듈(C, D)은 실행하지 않는다. 모든 판단이 동기적이므로 콜백이나 대기 로직이 없다.

## **B.2. 체크 순서 및 중단 조건**

| 순서 | 체크 항목 | 중단 조건 및 처리 |
| :---: | :---- | :---- |
| **①** | **forceDown** | true이면 즉시 중단. C·D 실행 안 함. A는 다음 앱 실행 시 재시도. |
| **②** | **allowAppVersion** | 현재 앱 versionCode \> 설정값이면 중단. 마켓 심사 중 버전 방어. |
| **③** | **launchUrl** | off이면 중단. 서버에서 mayLaunchUrl 기능 전체를 비활성화하는 스위치. |
| **④** | **activationRate** | 0\~100 난수 생성 후 비교. 미통과 시 중단. 통과 시 Module C로 결과 전달. |

| activationRate 값 | 동작 |
| ----- | :---- |
| **0** | 항상 미실행. LaunchUrlEngine 완전 비활성화. forceDown과 동일한 효과. |
| **10** | 앱 실행 10회 중 평균 1회 LaunchUrlEngine 실행. 나머지 9회는 확률 미통과로 중단. |
| **50** | 앱 실행 2회 중 평균 1회 실행. 트래픽 절반 제어. |
| **100** | 항상 실행. 확률 연산 없이 통과. 전체 사용자 대상 완전 활성화. |

## **B.3. activationRate 확률 연산 상세**

activationRate 값에 따른 동작과 연산 로직은 아래와 같다.

| 단계 | 처리 | 상세 |
| :---: | :---- | :---- |
| **1** | **설정값 읽기** | ConfigManager에서 activationRate 정수값 로드. 유효 범위는 0\~100. 범위 초과값은 0(미실행) 또는 100(항상 실행)으로 클램핑 처리. |
| **2** | **난수 생성** | 0\~99 범위의 정수 난수를 생성한다. 암호학적 강도는 불필요하며, 표준 의사난수(PRNG)로 충분하다. |
| **3** | **비교 연산** | 생성된 난수 \< activationRate 이면 통과(실행). 이상이면 미통과(중단). 예: rate=10이면 난수 0\~9(10개)일 때만 통과. |
| **4** | **결과 처리** | 통과: LaunchUrlEngine 진입. 미통과: LaunchUrlEngine 실행 없이 조용히 종료. 미통과 여부를 사용자에게 노출하거나 로그에 과도하게 기록하지 않는다. |

⚠ 확률 연산은 매 앱 실행마다 독립적으로 수행한다. '이번에 미통과했으니 다음엔 통과시킨다'는 보정 로직을 절대 넣지 않는다. 보정 로직은 장기적 분포를 왜곡하고 서버 의도와 다른 실행 패턴을 만든다.

## **B.4. 활용 시나리오**

| 상황 | 권장 rate | 이유 |
| :---- | :---: | :---- |
| **초기 출시 / PoC 검증 단계** | **5\~10** | 소수 사용자에게만 적용하여 영향도 측정. 문제 발생 시 즉시 0으로 원격 차단 가능. |
| **안정성 확인 후 단계적 확대** | **30\~50** | 절반 이하의 사용자에게 적용하며 서버 부하 및 쿠키 효과 모니터링. |
| **전체 운영** | **100** | 검증 완료 후 전체 사용자 대상 활성화. |
| **긴급 이슈 발생 시** | **0** | forceDown과 함께 즉각 실행 중단. 앱 업데이트 없이 서버 설정만으로 처리. |
| **특정 비율 A/B 테스트** | **원하는 %** | 타겟팅 쿠키 유효성과 광고 효과를 분할 실험으로 측정. |

## **B.5. 개발 시 주의사항**

* 확률 연산은 LaunchUrlEngine 진입 직전, 즉 ⑦단계에서만 수행한다. 로그 전송(⑥)은 확률 결과와 무관하게 항상 실행되어야 DAU 집계가 확률 편향 없이 정확하게 유지된다.

* activationRate가 설정 파일에 없거나 파싱 실패 시 기본값은 0(미실행)으로 처리한다. 값 부재를 100으로 처리하면 설정 파일 로드 실패 시 의도치 않은 전체 실행이 발생한다.

* 0과 100은 난수 생성 없이 즉시 결과를 반환한다. 불필요한 연산을 제거하고 동작 의도를 코드에서 명확히 한다.

* 확률 미통과는 오류가 아니다. 예외를 던지거나 에러 로그를 남기지 않는다. 단순히 LaunchUrlEngine을 시작하지 않고 조용히 종료한다.

✔ activationRate는 SDK의 트래픽 조절 다이얼이다. 앱 업데이트 없이 서버 설정 파일만 변경하면 언제든 실행 비율을 즉각 조정할 수 있다.

# **Module E — Log Reporter (독립 로그 전송)**

## **E.1. 독립 실행 원칙**

Log Reporter는 Config Loader(A) 완료 직후 Gate Checker(B)와 동시에 트리거된다. B의 통과/중단 결과, C의 환경 감지 결과, D의 호출 성공 여부와 완전히 무관하게 독립 실행된다. 어떤 모듈이 중단되어도 로그는 전송된다.

⚠ E가 독립 모듈인 핵심 이유: activationRate=10으로 설정하면 B에서 90%의 사용자가 중단된다. 로그가 B 내부에 있으면 DAU가 실제의 10%로만 집계된다. E의 독립성이 정확한 DAU 집계를 보장한다.

## **E.2. 로그 목적**

* 앱 실행 시마다 로그 URL 호출 → 서버에서 DAU(일간 활성 사용자) 집계

* 하루 중 반복 접속 횟수도 서버 측에서 동일 세션 기준으로 파악 가능

## **E.3. 기기 식별자 정책 원칙 (Android 정책 최우선)**

기기를 식별하는 수단 선택은 Google Play 정책 준수 여부가 기준이다. 정책 위반은 앱 삭제/리젝으로 직결되므로 어떤 기술적 이점보다 우선한다.

| 식별자 종류 | 사용 가능 | 판단 근거 |
| :---- | :---: | :---- |
| **IMEI / 기기 시리얼** | **✘ 사용 불가** | Android 10(API 29)부터 일반 앱 접근 완전 차단. |
| **Android ID (광고 목적)** | **✘ 사용 불가** | Google 정책: 광고 타겟팅 목적의 기기 추적에는 광고 ID만 허용. Android ID를 광고에 사용하면 앱 삭제 사유. |
| **광고 ID (Advertising ID)** | **✘ 사용 불가** | 사용자가 언제든 리셋·완전 차단 가능. Opt-out 시 추적 금지 의무 발생. 지속적 식별 수단으로 부적합. |
| **Android ID (통계 목적)** | **△ 조건부 허용** | 광고 목적이 아닌 앱 사용 통계·DAU 집계 목적에 한해 허용 가능. 단, 개인정보처리방침 명시 및 Data Safety 등록 필수. |
| **서버 발급 세션 토큰** | **✔ 권장** | 기기 고유 정보 미포함. 서버가 발급하는 랜덤 토큰을 앱 내 저장. 정책 리스크 없음. 쿠키와 연동 가능. |

⚠ 광고 ID(Advertising ID)를 사용할 경우 사용자가 '광고 추적 제한'을 설정하면 반드시 해당 기기에 대한 광고 타겟팅을 중단해야 한다. 이를 무시하면 Google Play 즉시 삭제 사유에 해당한다.

## **E.4. 채택 방식: 서버 발급 세션 토큰**

GG-SDK는 기기 고유 식별자 대신 서버가 발급하는 세션 토큰(sid)을 사용한다. 이 방식은 Android 정책 리스크가 없으며, 쿠키 기반 타겟팅과 자연스럽게 연동된다.

| 항목 | 내용 |
| :---- | :---- |
| **발급 시점** | 앱 최초 실행 시 서버에 토큰 발급 요청. 이후 앱 내 SharedPreferences에 저장하여 재사용. |
| **토큰 구성** | 서버가 생성하는 랜덤 UUID 형태. 기기 정보 미포함. 서버에서 관리·만료 처리. |
| **쿠키 연동** | mayLaunchUrl 호출 URL에 sid 파라미터 포함. 서버가 Set-Cookie 발급 시 sid와 쿠키를 서버 측에서 매핑. |
| **DAU 집계** | 로그 URL 호출 시 sid 포함 → 서버에서 sid 기준 일일 중복 제거 → 정확한 DAU 산출. |
| **토큰 갱신** | 앱 재설치 또는 앱 데이터 초기화 시 새 토큰 발급. 만료 정책은 서버에서 관리. |

✔ sid는 기기를 특정하는 정보가 아니므로 개인정보보호법상 개인정보에 해당하지 않는다. 다만 서버에서 행동 데이터와 결합 저장할 경우 개인정보로 전환될 수 있으므로 서버 측 데이터 관리 정책도 함께 수립해야 한다.

## **E.5. 로그 URL 파라미터 정의**

로그 URL 호출 시 아래 파라미터를 포함하여 GET 요청만으로 서버가 통계를 집계할 수 있도록 설계한다. 앱 내 별도 DB는 불필요하다.

| 파라미터 | 필수 | 설명 및 정책 근거 |
| :---- | :---: | :---- |
| **sid** | **필수** | 서버 발급 세션 토큰. 기기 고유 정보 미포함. DAU 중복 제거 및 쿠키 매핑에 사용. Android 정책 무관. |
| **av** | **필수** | 현재 앱 버전 코드(versionCode 정수). 버전별 로그 분리 목적. |
| **ts** | **필수** | UTC 타임스탬프(초). 하루 반복 접속 횟수 집계. 서버에서 날짜 기준 그룹핑에 사용. |
| **env** | **필수** | prod / dev 구분값. 서버 로그 필터링. DEV 로그가 실제 DAU에 포함되지 않도록 분리. |

✔ 로그 URL 호출은 비동기 fire-and-forget 방식으로 처리한다. 실패해도 재시도하지 않으며, 메인 쓰레드 및 LaunchUrlEngine에 영향을 주지 않는다.

# **Module C — Engine Launcher (환경 감지 및 실행 진입)**

Engine Launcher는 Gate Checker(B)가 통과 결과를 전달한 후 실행된다. B와 달리 비동기로 동작하며 두 가지 대기를 순서대로 처리한다. 첫째, EnvDetector를 통해 운영/개발 환경을 판별하고, 둘째, startDelay 타이머를 완료한 뒤 Launch Engine(D)을 호출한다.

## **C.1. 감지 기준: 홈화면 WebView URL (1차 감지)**

홈화면은 앱 실행 시 무조건 가장 먼저 로드되는 화면이다. 홈화면 WebView가 로드하는 centras.ai 광고 URL의 도메인이 운영계인지 개발계인지를 판별하여 SDK 환경을 결정한다. 이는 SDK 초기화 시점과 감지 시점이 일치하여 지연 없이 즉각 판단이 가능하다는 장점이 있다.

| 환경 | 홈화면 WebView 로드 URL | SDK LaunchUrl 동작 |
| :---- | :---- | ----- |
| **운영계 (PROD)** | ads.centras.ai/ad\_home.html | **✔ 정상 작동** |
| **개발계 (DEV)** | devads.centras.ai/ad\_home.html | **✘ 비활성화** |

✔ 홈화면 WebView는 앱 실행 직후 로드되므로 SDK 초기화와 타이밍이 정확히 일치한다. 활동탭과 달리 사용자 인터랙션(탭 이동) 없이도 즉시 환경 판별이 가능하다.

## **C.2. 감지 불가 시 보조 판별: 활동탭 WebView URL (2차 감지)**

홈화면 WebView URL이 onPageFinished 시점에 centras.ai 도메인을 포함하지 않거나 아직 로드되지 않은 예외적 상황에서는, 사용자가 활동탭으로 이동한 후 로드되는 WebView URL을 보조 감지 기준으로 사용한다.

| 환경 | 활동탭 WebView 로드 URL (2차) | SDK LaunchUrl 동작 |
| :---- | :---- | ----- |
| **운영계 (PROD)** | ads.centras.ai/ad\_activity.html | **✔ 정상 작동** |
| **개발계 (DEV)** | devads.centras.ai/ad\_activity.html | **✘ 비활성화** |

⚠ 2차 감지는 사용자가 활동탭으로 이동해야만 URL을 알 수 있다. LaunchUrlEngine은 1차 감지 완료 전까지 대기 상태를 유지하며, 2차 감지로 전환된 경우 활동탭 WebView onPageFinished 이후에야 실행을 시작한다.

## **C.3. 감지 우선순위 및 상태 흐름**

EnvDetector는 아래 순서대로 환경 판별을 시도하며, 한 번 확정된 결과는 앱 세션 동안 변경되지 않는다.

| 순서 | 조건 | 처리 |
| :---: | :---- | :---- |
| **①** | **홈화면 WebView onPageFinished 발생** | URL 도메인 확인. ads.centras.ai → PROD 확정. devads.centras.ai → DEV 확정. → LaunchUrlEngine 즉시 시작 or 비활성화. |
| **②** | **홈화면에서 감지 실패 (centras.ai 도메인 없음)** | EnvDetector를 PENDING 상태로 유지. LaunchUrlEngine 대기. |
| **③** | **사용자가 활동탭 이동 → onPageFinished 발생** | 활동탭 WebView URL로 2차 감지 시도. 도메인 확인 후 환경 확정. |
| **④** | **활동탭에서도 감지 실패** | 안전을 위해 DEV 환경으로 간주. LaunchUrlEngine 비활성화. |

⚠ ④ 감지 실패 시 DEV로 간주하는 이유: 운영 환경 판별 실패 상태에서 LaunchUrlEngine을 실행하면 의도하지 않은 쿠키가 실사용자 브라우저에 기록될 수 있어 더 위험하다.

## **C.4. 개발 시 주의사항**

* WebView URL 감지는 반드시 onPageFinished 콜백 시점에 수행한다. 페이지 로딩 중(onPageStarted)의 URL은 리다이렉트 전 주소일 수 있어 신뢰할 수 없다.

* URL 도메인 비교 시 toLowerCase() 정규화 후 contains 또는 startsWith로 비교한다. 대소문자 혼용 URL 방어 처리 필수.

* 홈화면 WebView가 먼저 로드되는 구조가 확정되어 있어야 1차 감지 로직이 안정적으로 작동한다. 앱 구조 변경 시 EnvDetector 재검토 필요.

* devDetector=off 설정 시 환경 감지 로직 전체를 건너뛰고 무조건 PROD로 취급한다.

# **Module D — Launch Engine (mayLaunchUrl 실행)**

Launch Engine은 Engine Launcher(C)가 PROD 환경 확정 및 startDelay 완료 신호를 전달한 후 실행된다. CCT 바인딩부터 URL 순차 호출, StateTracker 기록까지 mayLaunchUrl 실행의 전체 생명주기를 담당한다.

## **D.1. startDelay — C에서 D로 넘어오기 전 대기**

환경 감지(PROD 확정) 후 Launch Engine이 즉시 시작되지 않는다. Engine Launcher(C)가 설정 파일의 startDelay 값만큼 비동기 대기를 완료한 뒤 D를 호출한다.

| startDelay 값 | 동작 |
| ----- | :---- |
| **0** | 대기 없이 즉시 Module D 호출. 설정값 미기재 시 기본값. |
| **3 (권장 최솟값)** | 환경 확정 후 3초 대기. 앱 초기 로딩 자원 집중 구간 회피. |
| **5\~10 (일반 권장)** | 앱이 안정적으로 정착된 후 D 호출. 사용자 이탈 전 충분한 안착 시간 확보. |
| **30 이상 (보수적)** | 사용자가 앱 내 충분히 활동 중임을 확인 후 실행. 단, 짧은 세션 사용자는 D 실행 전 이탈 가능성 증가. |

⚠ startDelay 대기 중 앱이 백그라운드로 전환되면 C가 타이머를 취소하고 D를 호출하지 않는다. Handler.postDelayed 또는 코루틴 delay로 구현. Thread.sleep() 사용 금지(ANR 발생).

## **D.2. 실행 조건 최종 확인**

D는 C로부터 호출되기 전 아래 조건이 모두 충족된 상태임을 전제한다.

다음 조건을 모두 충족한 경우에만 LaunchUrlEngine이 시작된다.

* 설정 파일 로드 완료

* forceDown \= false

* 현재 앱 버전 ≤ allowAppVersion

* DEV 환경이 아님 (devDetector=on인 경우)

* activationRate 확률 통과

* launchUrl \= on

* startDelay 대기 완료 (대기 중 백그라운드 전환 없음)

## **7.2. startDelay — 실행 시작 지연**

모든 조건이 통과된 직후 LaunchUrlEngine은 즉시 CCT 바인딩을 시작하지 않는다. 설정 파일의 startDelay 값(초)만큼 비동기로 대기한 뒤 시작한다. 이 대기 시간은 앱 초기 화면 렌더링, WebView 광고 로딩, 네트워크 초기 요청이 집중되는 구간과 LaunchUrlEngine 실행을 분리하기 위한 것이다.

| startDelay 값 | 동작 |
| ----- | :---- |
| **0** | 대기 없이 즉시 CCT 바인딩 시작. 설정값 미기재 시 기본값으로 사용. |
| **3 (권장 최솟값)** | 조건 통과 후 3초 대기. 앱 초기 로딩 자원 집중 구간 회피. |
| **5\~10 (일반 권장)** | 앱이 안정적으로 정착된 후 시작. 사용자가 첫 화면을 충분히 인터랙션한 뒤 실행. |
| **30 이상 (보수적 운영)** | 사용자가 앱 내에서 충분히 활동 중임을 확인한 뒤 실행. 단, 사용 시간이 짧은 사용자는 실행 전 이탈 가능성 증가. |

✔ startDelay · cycleTime · ragTime 은 SDK 시간 축 3대 변수다. startDelay는 '언제 시작', cycleTime은 'URL 간 간격', ragTime은 '다음 사이클 간격'을 각각 제어한다. 서버 설정 파일만으로 언제든 조정 가능하다.

## **D.3. CCT 바인딩 및 세션 관리**

startDelay 완료 후 CCT 바인딩을 시작한다.

* CustomTabsClient.bindCustomTabsService()로 Chrome 서비스에 바인딩

* warmup(0) 호출로 브라우저 프로세스 사전 준비

* newSession()으로 고유 세션 생성

* 앱이 백그라운드로 전환될 때 서비스 연결 해제 (배터리 최적화)

## **D.4. URL 순차 호출 로직 (핵심)**

URL 리스트는 중요도 순서로 정렬되어야 하며, 아래 규칙에 따라 순차적으로 호출된다.

| 상황 | 동작 |
| :---- | :---- |
| **최초 실행 / 사이클 시작** | 리스트 0번 인덱스부터 시작. 각 URL 호출 후 cycleTime(초) 대기 후 다음 URL 호출. |
| **앱 이탈 (백그라운드/종료)** | 현재 호출 완료된 마지막 인덱스를 StateTracker에 저장. |
| **앱 재접속 (미완료 리스트 있음)** | 저장된 인덱스 다음 URL부터 이어서 호출 재개. |
| **전체 리스트 호출 완료** | 완료 시각을 StateTracker에 기록. RagTime 카운트 시작. |
| **RagTime 경과 후 재접속** | 0번 인덱스부터 새로운 사이클 시작. |
| **RagTime 미경과 재접속** | 호출 없음. 대기 상태 유지. |

⚠ 리스트 순서가 중요하다. 사용자가 앱을 짧게 사용하고 이탈하면 하위 인덱스 URL은 호출되지 않을 수 있다. 광고 타겟팅 우선순위가 높은 URL을 리스트 앞에 배치해야 한다.

## **D.5. URL 리스트 설계 가이드 — 세션 시간과 호출 현실**

URL 리스트는 최대 30개까지 등록 가능하지만, 실제 앱의 사용 패턴에 따라 한 세션에서 호출할 수 있는 수는 제한된다. 리스트를 설계할 때 이 현실을 반드시 고려해야 한다.

### **세션 시간과 호출 가능 수 관계**

아래는 startDelay=5초, cycleTime=3초 기준으로 한 세션에서 호출 가능한 URL 수를 계산한 예시다.

| 포그라운드 유지 시간 | startDelay 후 가용 시간 | 호출 가능 URL 수(cycleTime 3초) | 30개 기준 완료율 |
| :---: | :---: | :---: | :---: |
| 20초 | 15초 | **약 5개** | **17%** |
| 60초 (1분) | 55초 | **약 18개** | **60%** |
| 96초 (1분 36초) | 91초 | **30개 전체** | **100%** |
| 180초 (3분) | 175초 | **30개 전체** | **100%** |

⚠ 걷기 앱처럼 실행 후 빠르게 백그라운드로 전환하는 앱은 포그라운드 유지 시간이 20\~30초에 불과한 경우가 많다. 이 경우 30개 리스트 중 앞의 5\~8개만 안정적으로 호출된다.

### **URL 리스트 구성 전략**

리스트를 설계할 때는 아래 세 가지 원칙을 따른다.

| 원칙 | 내용 |
| :---- | :---- |
| **① 중요도 순 정렬 (필수)** | 가장 타겟팅 효과가 높은 URL을 0번 인덱스에 배치한다. 세션이 짧게 끝나도 가장 중요한 URL은 반드시 호출된다. 순서 변경은 서버 설정 파일만으로 즉시 반영 가능하다. |
| **② 현실적 URL 수 설계** | 앱의 평균 포그라운드 세션 시간을 먼저 파악한다. StateTracker 이어서 호출 기능을 고려해도 한 사이클 완료에 걸리는 세션 횟수가 너무 많으면 타겟팅 효과가 희석된다. 앱 사용 패턴에 따라 5\~15개를 현실적 운영 범위로 권장한다. |
| **③ 상위 URL 직접 관리 (운영 정책)** | 리스트 전체를 자동화하기보다, 상위 5\~8개 URL은 담당자가 직접 순서와 내용을 관리한다. 이 구간이 실질적인 타겟팅 효과의 대부분을 담당하기 때문이다. 하위 URL은 보조적 효과로 인식하고 운용한다. |

### **StateTracker 이어서 호출과의 관계**

URL 30개를 한 세션에 모두 호출하지 못하더라도 StateTracker가 마지막 인덱스를 저장하므로, 사용자가 다음에 앱을 실행하면 이어서 호출된다. 이 구조 덕분에 세션이 짧은 앱에서도 전체 리스트를 여러 세션에 걸쳐 완료할 수 있다. 단, 아래 한계를 인식하고 리스트를 설계해야 한다.

| 고려 항목 | 내용 |
| :---- | :---- |
| **사이클 완료까지 걸리는 세션 수** | URL 30개, 세션당 평균 5개 호출 시 → 6번 앱 실행해야 1사이클 완료. ragTime이 짧으면 다음 세션에서 새 사이클로 리셋될 수 있어 하위 URL은 영구 미호출 될 가능성 존재. |
| **ragTime 설계 시 주의** | ragTime은 '전체 리스트 완료 후' 카운트 시작이므로 완료 전에는 리셋되지 않는다. 그러나 URL 수가 많고 세션이 짧을수록 완료 자체가 오래 걸린다. |
| **앱 삭제/재설치 시 초기화** | StateTracker는 SharedPreferences 기반이므로 앱 재설치 시 진행 상태가 초기화된다. 재설치 사용자는 항상 0번 인덱스부터 시작한다. |

✔ URL 리스트는 코드가 아닌 서버 설정 파일로 관리된다. 순서 변경, 추가, 삭제 모두 앱 업데이트 없이 즉시 반영 가능하다. 운영 중 앱의 실제 세션 시간 데이터를 Log Reporter 로그로 파악한 뒤, 리스트 수와 순서를 지속적으로 최적화하는 것을 권장한다.

## **D.6. StateTracker — 호출 상태 영속화**

앱 재실행 후에도 호출 진행 상태를 유지하기 위해 SharedPreferences에 아래 정보를 저장한다.

* lastCalledIndex: 마지막으로 호출 완료된 URL 인덱스

* completedAt: 전체 리스트 완료 시각 (Unix timestamp)

* cycleComplete: 현재 사이클 완료 여부 (boolean)

* sid: 서버 발급 세션 토큰. 앱 재설치 전까지 동일 값 유지하여 URL 호출 시 일관된 식별자 전달.

## **D.7. 개발 시 유의사항**

* startDelay 대기는 Handler.postDelayed 또는 코루틴 delay 등 비동기 방식으로 구현한다. Thread.sleep() 사용 금지 — 메인 스레드를 블로킹하면 ANR이 발생한다.

* startDelay 대기 중 앱이 백그라운드로 전환되면 대기 타이머를 즉시 취소한다. 백그라운드 상태에서 CCT 바인딩을 시작하면 시스템이 프로세스를 강제 종료할 수 있다.

* startDelay 값이 설정 파일에 없거나 파싱 실패 시 기본값은 0(즉시 시작)으로 처리한다.

* mayLaunchUrl은 성공을 보장하지 않는다. 시스템 리소스 부족 시 무시될 수 있으므로 100% 실행을 전제로 한 로직을 구성하면 안 된다.

* CCT 바인딩 실패(Chrome 미설치 기기 등) 시 예외 처리를 반드시 구현하고, 실패해도 앱 메인 로직에 영향을 주지 않아야 한다.

* cycleTime은 너무 짧게 설정하면 시스템이 throttling할 수 있다. 최소 1\~3초 이상을 권장한다.

* 앱 생명주기(onPause/onStop/onDestroy)와 CCT 서비스 바인딩 해제를 반드시 연동한다.
